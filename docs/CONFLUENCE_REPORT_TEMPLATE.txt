*報告日期*：2026-03-11
*對象*：KKday QA 團隊
*主旨*：針對 3/1 以來 QA Automation 資料庫修復、TCMS 1.5 升級衝擊及系統隔離工程之全面檢討。

---

h2. 1. 事前背景 (Context)
自 3 月初起，團隊開始進行 TCMS 1.5 的後端 API 開發與前端架構優化。在此過程中，頻繁進行資料庫 Migration (Alembic) 與測試數據填充。

h2. 3. 根本原因分析 (Root Cause Analysis)

# *缺乏資料隔離 (Lack of Isolation)*：新系統與舊系統共用同一個資料庫 schema。開發中的 Migration 腳本誤觸或覆蓋了舊系統的實體表。
# *備份機制不完備*：事故發生前，缺乏自動化的每日備份與異地存檔。
# *高權限 AI 操作風險*：AI 輔助工具使用 admin 超級管理員帳號，且缺乏明確的 DDL 操作約束。

---

h2. 4. 已執行的修正行動 (Actions Taken)

* *物理隔離 (Physical Decoupling)*：已準備好切斷 View 連結。未來新舊系統將各自擁有獨立實體表（如 users 與 tcms_users）。
* *受限帳號管理 (ai_worker)*：已建立專屬 AI 帳號：具備「查增改」權限，但嚴禁「刪除」與「毀壞結構」。
* *自動化備份機制*：已部署 db_backup.sh 與 Cron Job，確保每日自動產出壓縮備份。
* *建立防護規範 (.ai_rules.md)*：在專案根目錄硬性規範 AI 行為。

---

h2. 5. 未來建議與預防措施 (Prevention & Recommendations)

* *落實「保守還原」模式*：還原資料庫時優先使用不刪除資料的覆蓋模式。
* *資料定期查驗*：建議每週執行資料量比對 SQL，確保隔離機制未失效。
* *版本控制與 Migration 嚴格審查*：所有遷移檔執行前需檢查是否包含針對非 tcms_ 表格的 DROP 指令。
* *異地備份*：考慮將備份檔定期上傳至雲端儲存 (如 S3)。

---
*總結*：本次事故促成了系統架構的健康化。目前的「隔離＋備份＋受限權限」方案已能大幅降低未來資料損毀風險。
